# AgentGate — Wedge decision before implementation

**Decision date:** 2026-10-05  
**Status:** Product hypothesis and validation gate; [ARCHITECTURE.md](ARCHITECTURE.md) records a conditional narrow design, but implementation remains NO-GO pending [VALIDATION_PLAN.md](VALIDATION_PLAN.md).  
**Read together with:** [PRODUCT.md](PRODUCT.md), [MVP.md](MVP.md), [ECOSYSTEM.md](ECOSYSTEM.md).

## 1. Decision context and hard constraints

The broad product in PRODUCT.md and the gateway walkthrough in MVP.md are **not differentiated**. Archestra, agentgateway, Permit, ActionProxy, ContextForge, Docker's MCP products, and smaller open-source gateways already cover material parts of identity, tool policy, approval, and audit. A smaller implementation of the same checklist is not by itself a wedge. The competitive inventory and protocol analysis in [ECOSYSTEM.md](ECOSYSTEM.md) are constraints, not a list of optional features.

The current [MCP specification](https://modelcontextprotocol.io/specification/2026-07-28) is 2026-07-28. The 2025-11-25 and 2026-07-28 wire contracts differ substantially: legacy initialization/session handling versus modern per-request metadata and HTTP headers. Tool discovery may paginate and vary by authorization; filtering a list does not enforce a call. OAuth audience and downstream authority are separate from an arbitrary agent label. A gateway on one configured path cannot claim to protect direct bypasses or host-native tools. These points are established in ECOSYSTEM.md and the [official versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), and [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) documents.

**Evidence standard:** Product READMEs establish claimed features, not comparative performance or production quality. An issue or test demonstrates one reproducible problem, not prevalence. We have **not** run competitor quickstarts, interviewed target users, or measured install times. “No documented feature in the reviewed sources” does not mean a product lacks it. Acquirer interest, adoption, and relative quality are hypotheses.

## 2. Scoring method

Nine scores are each **1–5; higher is better**. S = problem severity; E = evidence of experienced developer pain; C = competitive headroom (5 means little direct competition); F = feasibility for a small OSS team; T = demonstrable value in under five minutes; O = organic adoption potential; D = defensibility; A = plausible strategic acquisition value; X = ability to expand into a larger AgentGate product. Scores are judgments, **not market measurements**. Equal-weight total /45 is a comparison aid, not a verdict: an already adequately served job can be eliminated regardless of total. Acquisition scores are especially speculative.

**Important nuance:** A gateway's own policy unit test or audit log is helpful, but a response saying “denied” does not independently establish that the upstream server never received the call. Conversely, an isolated mock upstream proves only that *this test path* did not forward, not that real deployments cannot bypass the gateway. The [OWASP harness](https://github.com/OWASP/Agent-Security-Regression-Harness) already tests denied *agent tool calls* in traces; AgentGate would need to validate the **enforcement boundary**, a distinct assertion. The [official suite](https://github.com/modelcontextprotocol/conformance) is the authority on revision-specific protocol conformance; AgentGate should use or contribute to it instead of claiming to replace it.

## 4. Candidate judgments and kill conditions

1. **Local-first (#1):** Ease of setup is a plausible job, but ActionProxy already supplies a local demo and several small projects supply local enforcement. Only revisit if a timed, reproducible trial with real developers shows a large advantage on the **same** authenticated client/server path and policy outcomes. “One binary” or “no dashboard” is insufficient.
2. **Conformance-first gateway (#2):** Compatibility failures are serious, especially across revisions, but Archestra already advertises dual-era support and the official suite supports per-revision checks. A small team would own two wire roles, auth behavior, streaming, discovery and error semantics. Contribute gateway cases to the official suite if possible; a new production proxy is unjustified by conformance alone.
3. **Coding agents (#3):** The agents named in the prompt do not share one verified MCP auth, approval, stdio and HTTP UX. A label saying “built for coding agents” is marketing until a repeatable failure in one named host and a working comparison against Docker/ActionProxy/Archestra exists. Native shell/tools and direct server connections remain outside MCP interception.
4. **Argument authorization (#4):** A severe and concrete need: one SQL/query/shell tool can have radically different effects based on arguments. But MCPZT, mcp-gate and mcpwall already document argument-aware policies, and agentgateway can express conditions at the appropriate policy layer. A bespoke policy language is a high-maintenance duplicate. Test incorrect placement and bypasses rather than pitching the feature.
5. **Exact approval (#5):** Strong safety invariant, but ActionProxy, PermitRail and MCPZT document exact one-use or input-bound grants; Permit and Archestra document approvals. Cryptographic signatures do not make a gateway uniquely safe. The current MVP's manual error-and-retry flow is explicitly not guaranteed to work naturally in arbitrary hosts. Do not ship another approval UI as the wedge.
6. **Fail-closed verification (#6):** The user needs to know whether a configured DENY prevents execution, not merely whether the client sees an error or a tool is hidden from discovery. A black-box check of a real configured gateway with a controlled upstream could be a small independent developer tool. It must report inconclusive for bypass paths, unavailable observation, unsupported protocol flows and ambiguous side effects. This is the best hypothesis, but competitors could add the check quickly.
7. **Embeddable library (#7):** PermitRail already ships core/MCP gateway packages; ActionProxy has an SDK; OPA/Cerbos supply mature decisions. A library is a distribution form, not a unique job. Consider a reusable testing library only if #6 earns demand.
8. **Preflight/lint (#8):** The agentgateway issue shows a useful class of mistake: a rule may parse and report healthy while it is ineffective or overly permissive. A narrowly specified check for one documented configuration could help. Cross-vendor generic policy lint is not credible without understanding each engine's evaluation phase. Prefer reproducing the behavior through #6; upstream the engine-specific validation fix.

## 5. Recommended revised product direction

**PIVOT from a runtime security gateway to an independent, local MCP authorization regression test tool.** This is a *product direction*, not an architecture. The smallest potentially useful job is to let a gateway maintainer/developer run a controlled, authenticated policy test and see whether an intentionally denied `tools/call` was blocked **before upstream invocation**, with a positive ALLOW control proving the path actually works. The first version is about **observable enforcement**, not a complete security certification, full protocol conformance, red teaming, or operating a production gateway.

**Provisional v0.1 boundary, to validate before implementation:**

- One specified **2026-07-28 Streamable HTTP** client → existing gateway → controlled upstream MCP server path; document exact host/transport/auth assumptions. The original MVP's 2025-only runtime promise is withdrawn for this proposed direction. Any extra revision is tested separately, never inferred.
- One operator-supplied valid test credential and a denied tool on the configured gateway; a controlled harmless upstream counter/record shows zero `tools/call` invocations for DENY. An ALLOW case shows one invocation so an unconnected or always-denying gateway cannot pass.
- One negative case for direct invocation of a tool hidden from `tools/list`, plus a changed-argument or identity case **only where the gateway claims that policy**. A local, repeatable result explains what was sent, what response occurred, and what the upstream observed. Redact credentials and sensitive arguments by default.
- Failed setup, wrong version, unobservable upstream, bypassable route and uncertain result are explicit **INCONCLUSIVE/FAIL**, never a green security badge. A timeout after a forwarded call cannot prove whether a side effect happened.
- No requirement that an arbitrary third-party production upstream expose test-only counters. The first external adopter must be able to use a disposable server and their actual configured gateway. The exact mechanism and CLI syntax remain undecided pending validation.

**What must be noticeably better:** In a timed head-to-head against official conformance + Inspector + OWASP's harness + the gateway's own test/dry-run, produce a reproducible *upstream-observed* DENY result and a working ALLOW control for a named gateway with less manual scripting. The proof must distinguish “client received DENY,” “server observed zero calls,” and “path not actually tested.” If this takes more than five minutes after a documented demo setup, the sub-five-minute value claim is unproven. Interoperability across two named gateways would be a stronger adoption signal than a polished demo against a toy gateway.

**Deliberately do not build:** a runtime proxy/gateway, agent identity issuer, policy engine/language, approval queue or signing service, audit database, dashboard, cloud control plane, SSO, billing, DLP/prompt-injection scanner, security certification, or universal support for coding agents and every MCP revision. Do not maintain a competing replacement for the official conformance suite. Do not claim to prevent direct bypasses.

## 6. Validation gates before implementation code

1. **User evidence:** Speak with at least five maintainers/developers who actually configure MCP policy. Record current testing method, recent misconfiguration, impact, and whether they would run an independent check in CI. Demand is not yet verified by public docs.
2. **Head-to-head baseline:** Run the quickstarts for Archestra, agentgateway, ActionProxy, and at least one of ContextForge/Docker in a reproducible setup. Run official conformance/Inspector and inspect OWASP's harness. Time an external developer's journey from a documented gateway policy to an observed DENY/ALLOW result. Record limitations and maintainers' existing tests.
3. **Feasibility discovery:** Confirm two independent gateways can expose a controlled upstream on a documented 2026 path without modifying the gateway or giving the test tool production secrets. Check header/body agreement, auth failures and error semantics against the official specification. Determine what the test can and cannot observe.
4. **Proceed threshold:** At least two unrelated external developers report this exact unsolved job; two named gateways lack an equivalently quick upstream-observed check in the measured workflow; and a credible walkthrough can show denied zero-upstream plus allowed one-upstream in under five minutes after setup. These are proposed decision thresholds, not achieved results.
5. **Stop or contribute:** If official conformance, OWASP, or gateway-specific tests already solve this workflow adequately, contribute the missing scenario or documentation there. Do not create AgentGate as a parallel project merely to repackage them.

This decision **supersedes the proposed v0.1 product direction** in PRODUCT.md and MVP.md if the pivot is validated. Those documents are marked as historical proposals. [ARCHITECTURE.md](ARCHITECTURE.md) is a conditional design for the revised direction; [VALIDATION_PLAN.md](VALIDATION_PLAN.md) and [IMPLEMENTATION_READINESS.md](IMPLEMENTATION_READINESS.md) gate implementation. The old gateway CLI and approval contract are not requirements for the revised product.

## 7. Final decision

- **Top 3 viable directions, conditional:** **(1) #6** upstream-observed fail-closed authorization regression checks as a standalone developer tool; **(2) #8** tightly scoped policy misconfiguration preflight as a supporting test, never generic cross-engine lint; **(3) #2** revision-specific security/conformance cases contributed to the official suite or used within #6, **not** a new conformance-first runtime gateway. Only #6 has a plausible independent product path on the current evidence; #8 and #2 may be contributions/features rather than separate products.
- **Recommended wedge:** #6, narrowed to **black-box proof of DENY at the MCP gateway boundary with an ALLOW control**.
- **One-sentence positioning:** “AgentGate lets MCP gateway developers prove that a denied tool call never reaches a controlled upstream server, while a permitted call still works.”
- **Exact v0.1 user:** A developer or maintainer who owns a configured **2026-07-28 Streamable HTTP MCP gateway** and can point it at a disposable upstream server for local/CI testing.
- **Exact v0.1 job-to-be-done:** “Before shipping a policy change, I need a repeatable test that shows my denied tool call did not reach the upstream server and my allowed call did, using the actual gateway configuration.”
- **Noticeably better than competitors:** Evidence from upstream observation, positive control, explicit inconclusive outcomes, and faster reproducible setup on two real gateway products than stitching together protocol conformance, Inspector, trace assertions and vendor-specific dry-runs.
- **Do not build:** A production enforcement gateway or the postponed platform/approval/identity features listed above.
- **Recommendation: PIVOT, contingent on validation.** Stop the original runtime gateway implementation plan now. If the evidence gates fail, **STOP** the independent AgentGate product and contribute improvements to existing projects.
