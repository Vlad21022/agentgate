# AgentGate — MCP Ecosystem and Competitive Landscape

**Research date:** 2026-10-05  
**Status:** Pre-architecture research; no implementation recommendation is implied.  
**Evidence standard:** Protocol facts below come from the published MCP specification. Product capabilities come from the vendors' or projects' own documentation and repositories; they are **documented claims, not independently tested performance or completeness**. Inferences and unanswered questions are labeled separately. Links point to first-party sources.

## 1. Executive assessment

The published MCP revision is **2026-07-28**. It materially changes the wire protocol from the **2025-11-25** revision named in [MVP.md](MVP.md): the modern revision has self-contained requests instead of an initialization handshake and protocol session, and Streamable HTTP mirrors method and tool metadata in headers. Both eras matter for interoperability. [Specification](https://modelcontextprotocol.io/specification/2026-07-28) · [Versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) · [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

The generic proposition **“agent identity + per-tool permissions + audit” is already offered by several gateways**. Some also document per-call human approval. AgentGate cannot claim a unique feature set from those three outcomes alone. A narrow, independently verified developer experience or protocol-conformance advantage is a *hypothesis*, not an established differentiation. See the competitor table and validation gates below.

## 2. Verified MCP facts

| Topic | Verified behavior | Consequence for an intermediary | Primary source |
| --- | --- | --- | --- |
| Roles and messages | An MCP **host** runs a **client** connector to an MCP **server**. Messages use JSON-RPC 2.0. Servers expose tools, resources, and prompts; clients/hosts decide how to present and use them. | AgentGate would be a server-facing endpoint to the upstream client and a client to the downstream server. “Agent” is an application concept, not an automatically authenticated protocol principal. | [Specification overview](https://modelcontextprotocol.io/specification/2026-07-28) |
| Transports | Standard bindings are **stdio** (newline-delimited JSON-RPC over a launched subprocess) and **Streamable HTTP** (one POST per message; JSON or request-scoped SSE response). Custom transports exist. | A remote HTTP gateway does not automatically cover stdio or custom connections. A stdio wrapper must be explicitly configured as the launched server. | [Transport overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) · [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| Discovery | A server supporting tools advertises that capability; the client calls `tools/list`, possibly with pagination. The list can vary with **per-request authorization** and may change. The 2026 revision includes `ttlMs` and `cacheScope` on list results. | Filtering only one page or serving an agent-specific list from a shared cache can leak or misstate available tools. Hiding a tool never replaces checking `tools/call`. | [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) |
| Invocation | `tools/call` names a tool and carries arguments; results can include text, media, resources, and structured content. A tool-level failure can be returned as `isError`; protocol-level errors are distinct. Tool annotations are **untrusted** unless the server is trusted. | Enforce before forwarding; preserve result/error types, schemas, and streaming behavior. Do not infer safety solely from `readOnlyHint` or descriptions. | [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) |
| Modern lifecycle | In **2026-07-28**, every request carries version and client capabilities in `_meta`; there is no `initialize` handshake or `Mcp-Session-Id`. `server/discover` is available. HTTP requests carry matching `MCP-Protocol-Version`, `Mcp-Method`, and, for a tool call, `Mcp-Name` headers. Annotated parameters may be mirrored as `Mcp-Param-*` headers. Header/body mismatches are rejected. | An HTTP edge can route on headers, but an enforcing gateway that parses the body must validate their agreement, including encoded values. Client-reported `clientInfo` is metadata, not proof of identity. | [Versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) · [Streamable HTTP headers](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| Modern interactions | The 2026 revision uses `input_required` and multi-round-trip requests for server needs such as elicitation. Long-lived change notifications use `subscriptions/listen`. A request-scoped SSE stream can carry progress before its final response. | An approval mechanism cannot assume a legacy, held-open call or turn a supported interaction into an unrelated error while claiming transparent compatibility. The gateway must be explicit about which interactions it supports or rejects. | [Tools: input required](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| Legacy lifecycle | **2025-11-25** begins with `initialize` and capability negotiation. Legacy Streamable HTTP can use a session and GET/SSE behavior and can carry server-to-client requests. | A 2025 proxy has session, initialization, and potentially bidirectional message obligations that a naïve POST filter misses. It cannot simply assume the 2026 envelope. | [2025 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) · [2025 transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) · [2026 backward compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| Authentication and authorization | HTTP authorization is optional in MCP, but a protected server acts as an OAuth resource server and a client acts as an OAuth client. Protected resource metadata, authorization-server discovery, token audience, and per-request bearer usage matter. Stdio normally obtains credentials from its environment rather than the HTTP OAuth flow. | A static AgentGate bearer token may suit a configured local integration, but **is not by itself MCP OAuth interoperability**. Never forward a token issued for the gateway as if it were an upstream token; upstream identity/delegation is a separate problem. | [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) |
| HTTP endpoint safety | Streamable HTTP servers must validate the `Origin` header when present, should bind to loopback for local use, and should authenticate connections. | A local gateway still needs endpoint protections; a loopback URL alone is not a complete security boundary. | [Streamable HTTP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |

**Terminology:** Authentication establishes who/what holds an accepted credential; authorization decides whether that principal may perform this call. `clientInfo` and the model's self-description are not authenticators. A shared upstream service credential does not propagate the original human's permissions. This is an inference from the protocol's OAuth roles and token-audience rules, not a new protocol requirement. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

### The existing MVP's compatibility gap

[MVP.md](MVP.md) deliberately pins **2025-11-25**, uses static per-agent bearer tokens, and returns an `isError: true` / `APPROVAL_REQUIRED` response followed by a manually repeated call. That is a bounded, developer-controlled demonstration, **not** a guarantee that arbitrary MCP hosts will authenticate, wait, retry, or resume the action automatically. The current specification supports a different 2026 request model and `input_required` mechanism; neither automatically proves that a separate *operator*, rather than the agent's own user, approved a side effect. [Modern versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) · [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

Before coding, make the v0.1 claim precise: either “tested only with named 2025-11-25 client/server integrations” or a separately tested dual-era contract. Do not call a 2025-only prototype a transparent current-MCP gateway. This is a **recommendation inferred from the verified revision differences**, not a settled architecture decision.

## 3. Where policy can intercept traffic

| Interception point | What can be governed | Compatibility and trust conditions |
| --- | --- | --- |
| **MCP-aware HTTP gateway** with the client pointed at its URL | Authenticate the inbound caller; filter `tools/list`; decide before `tools/call`; log observed decisions and results. | This is the direct AgentGate path. It must behave as both an MCP server and client for each supported revision, keep session or per-request state as required, handle pagination/cache/notifications/streams, and preserve OAuth challenges or use separate valid upstream credentials. Direct connections around it remain outside scope. [2026 transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) · [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) |
| **HTTP edge proxy** inspecting modern request headers | Coarse routing, metering, or tool-name authorization on `Mcp-Method` / `Mcp-Name`, with optional parameter headers when the schema declares them. | Headers are useful in 2026, but must match the body. They are absent or different in legacy traffic; arbitrary arguments are not necessarily mirrored. A plain WAF cannot safely infer all tool semantics. [Request metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| **stdio subprocess wrapper** named as the host's MCP server | Parse and mediate local tool discovery and invocation. | Only applies to hosts configured to launch the wrapper. Preserve framing and lifecycle; never write non-MCP logs to stdout. HTTP OAuth assumptions do not transfer. [stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) |
| **Server middleware/SDK hook** | Enforce at the server, with direct access to server auth context and action semantics. | Stronger protection when the server owner can change code; no general drop-in proxy promise. Existing gateways and policy engines can use this placement. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) |

**Not interceptable by this gateway:** a client's direct connection to the upstream MCP server, built-in host tools, arbitrary shell/network operations, other transports not wrapped, or a downstream side effect whose outcome is lost after a timeout. These are scope inferences from the placement above. No audit entry can prove that an external side effect did not happen merely because a response was lost.

### Adjacent policy engines

[Open Policy Agent](https://www.openpolicyagent.org/docs/integration), [Cerbos with agentgateway](https://www.cerbos.dev/ecosystem/agent-gateway), and [OpenFGA](https://openfga.dev/) can provide authorization decisions or models. They are **not, by themselves, an MCP wire-compatible gateway with an approval lifecycle**. They could, however, make a bespoke AgentGate policy language redundant and let a mature gateway supply the enforcement point. This is an integration/positioning inference, not a claim about every deployment.

## 5. Assumptions and unanswered questions — not verified facts

| Hypothesis or unknown | Why it matters | Evidence needed before architecture |
| --- | --- | --- |
| External developers want a **small, local, configuration-first** gateway despite the options above. | The central product wedge is not yet demonstrated. | Five to ten interviews and a timed comparison against at least two direct open-source alternatives. |
| A static bearer token per agent is accepted by the target MCP hosts. | Some clients favor OAuth discovery or cannot supply a custom header; a protocol-compliant protected HTTP experience may require more than a static key. | Connect at least two named host clients and one custom SDK client; record auth and failure behavior per revision. |
| The `APPROVAL_REQUIRED` error plus manual identical retry is useful to developers. | It preserves a fail-closed tool call but can be awkward or non-recoverable in existing host UIs. | Observe a real user completing approval and retry in each target client; compare with a held call and modern `input_required` where appropriate. |
| A gateway can faithfully proxy the chosen 2025 subset while rejecting everything else. | Sessions, SSE, server-to-client requests, pagination, error surfaces and OAuth challenges may interact. | Versioned conformance tests and an explicit supported-method matrix; no unsupported pass-through. |
| “Agent identity” from a per-integration secret is sufficient. | Shared or stolen credentials identify the integration, not necessarily a model or human. Shared upstream credentials can broaden effective authority. | Threat model, token rotation test, bypass test, and a downstream-permission scenario. |
| A local JSONL audit is valuable enough without durable approval history or verified operator identity. | Investigation, side-effect uncertainty and regulatory expectations may demand more. | Show real incident questions to target users; verify exactly which fields and retention they require. |
| A narrow feature set can compete with established free or commercial gateways. | Several direct competitors already describe the same three outcomes. | A reproducible comparison: setup time, protocol conformance, fail-closed behavior, and documentation clarity. |

## 6. Decision gates before proposing an architecture

1. **Select the supported protocol contract openly.** Reconcile [MVP.md](MVP.md)'s 2025-11-25-only target with the published 2026-07-28 revision. Specify client, server, methods, transport, auth mode, approval behavior, and unsupported operations.
2. **Run a competitor quickstart.** At minimum compare agentgateway or ContextForge, Archestra, and one local approval project. Record what works, not only what the project claims.
3. **Prove one differentiated job.** Find an external developer who needs a task those alternatives cannot complete acceptably, or whose setup is materially simpler with AgentGate. “Identity, permissions, audit” alone does not satisfy this gate.
4. **Test three invariants across the supported path.** A denied call never reaches upstream; an approval is bound to the exact principal/action/arguments and consumed once; logs distinguish decision from unknown upstream outcome. Test direct bypass and lost-response behavior explicitly.
5. **Choose build, contribute, or narrow.** If existing open-source gateways meet the same job, consider contributing a small approval or conformance module to one of them. If AgentGate remains independent, document the measured wedge before implementation.

**Conclusion (inference):** The need for governance is real, but the broad AgentGate idea is already crowded. The strongest immediate risk is building a 2025-only local proxy that duplicates existing allow/deny/approval/audit projects while promising general MCP compatibility. Product differentiation and protocol scope must be validated before architecture.
